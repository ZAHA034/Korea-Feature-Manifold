# 0005-측정·모델 분리와 파생 테이블

- 상태: 제안 (0단계에서 확정)
- 날짜: 2026-10-20(제안), 2026-10-20(검토 반영 수정: 1항, 열린 점)
- 관련: PLAN G3, G4, G7, G8(연결선·속도 규칙), G9, 5.1·5.3절 / DESIGN 3장, 4.2 / ADR 0002·0004·0010·0012·0013

## 배경
DESIGN 3장은 1–3층을 관측, 4층을 모델로 나누지만 4.2의 테이블에는 계산값이 섞여 있다(`regions`의 지형 요약과 중심점, `links.travel_time`). 4층 산출물(거리 행렬, 곡률, 임베딩, 생활권, 배분)을 담을 테이블이 없어서 CLAUDE.md의 "임베딩과 왜곡 지표를 함께 저장" 규칙도 저장할 곳이 없다. 통근·통학 인원이나 인구이동처럼 통행/일이 아닌 관측 상호작용도 둘 곳이 없다.

## 선택지
계산값을 1–3층 테이블의 컬럼으로 두기 / 4층에 `run_id`를 키로 하는 파생 테이블로 나누기.

## 결정
1. 분리 규칙: 1–3층(관측)에는 원천이 준 값과, `ingest`가 실행 설정 없이 원천과 코드만으로 만드는 값(단위·좌표·코드 변환, 대응표로 옮긴 값, 인구 가중 중심·지형 요약 같은 집계)만 둔다. 옮긴 값에는 표시 컬럼(`derived_via`, `crosswalk_id`, `split_assumed`)을 단다. 실행 설정(`config`)이 있어야 계산되는 값은 4층에 둔다. 1–3층 테이블에는 `run_id`가 없고, 4층 테이블과 실행 기록 `runs`(어느 층에도 속하지 않는 메타 테이블)의 키에는 `run_id`가 있다(스키마 검증으로 확인). 1–3층은 `data/processed/`에, 4층과 `runs`는 `data/derived/run_id=<id>/`에 둔다(PLAN 5.1, ADR 0006 8항).
2. 점(G3): `region_points`(region_id, kind, ref_date, geometry, source_id)를 둔다. `kind`는 `pop_weighted`(인구 가중 중심, 통행시간의 출발점)와 `pop_max_dong`(인구가 가장 많은 행정동의 대표점)이다. 인구 가중 중심이 자기 지역 밖에 있으면 `pop_max_dong`을 출발점으로 쓴다(0S에서 옹진·신안·통영·완주). `regions.centroid`는 두지 않고, 기하 중심이 필요하면 geometry에서 계산한다.
3. 지형 요약(G4): `elev_mean`, `elev_std`, `slope_mean`을 `region_attributes`의 지표로 옮기고 `indicators`에 등록한다. DEM 버전은 `source_id`로 추적한다. 지형 요약은 대응표로 옮기지 않고 해당 경계에서 DEM으로 다시 계산한다.
4. 관측 상호작용(G7): `links`에는 관측값과 출처가 제공한 값만 둔다(KTDB OD의 `flow`, 시간표의 소요 시간 등). 도로망으로 계산한 통행시간은 `travel_time_matrix`에, 추정 OD는 `od_estimates`에 두며 `method`로 "추정 OD"를 표시한다.
   - 통행/일이 아닌 관측 상호작용은 `interactions`(from_id, to_id, kind, ref_period, value, unit, source_id, crosswalk_id, split_assumed)에 둔다. `kind`는 `commute`, `migration`이고 `ref_period`는 원천의 기간(`2020`, `2025`, `2025-03`)이다. 다년 합산은 저장하지 않고 계산 단계에서 한다.
   - 값이 표본 추정치이면 표본 비율(통근·통학 2020은 20%)을 `sources`에 적고, 유효 표본 수 계산(ADR 0010 6항)이 이를 읽는다.
   - 어느 OD를 썼는지는 `runs.data_snapshot`에 남긴다.
5. 망과 연결선(G8): 망 테이블의 구조와 지역 귀속은 ADR 0012를 따른다. 원천의 길이는 수집 단계에서 km로 바꾼다(`length_km`). 연결선(지역 출발점 → 도로 노드 k개)의 개수·접근 속도와 링크 통행시간의 속도 규칙(등급별 기본 속도, 전역 속도 계수)은 설정 값이다. 설정 값은 `config_json`과 `config_hash`에 들어가고 데이터 테이블에는 넣지 않는다. 연결선과 링크 통행시간은 4층 산출물이다.
6. 파생 테이블(G9): PLAN 5.3 (나)의 13개 테이블과 키를 채택한다. 컬럼은 해당 단계의 ADR이 채택될 때 보강한다. 이미 정해진 보강은 `embedding_distortion`의 `converged`·`n_iter`(ADR 0013)와 `metric_diagnostics`의 `role`·`replicate`(ADR 0010)다. 임베딩 저장 함수는 `embeddings`, `embedding_distortion`, `embedding_worst_pairs`가 모두 있을 때만 쓰고 하나라도 없으면 예외를 낸다. CLAUDE.md의 왜곡 지표 동시 저장 규칙을 API로 지키기 위해서다.
7. 컬럼 정리: `regions`에서 `source_code`(→ `region_codes`, ADR 0002), `elev_mean`·`elev_std`·`slope_mean`(→ `region_attributes`), `centroid`(→ `region_points`)를 뺀다. `network_edges`의 `road_rank`, `lanes`, `max_speed`, `observed_volume`은 ADR 0012의 확장 테이블로 간다.

## 영향
- DESIGN.md 수정 절: 4.2(`regions` 컬럼 정리, `region_points`·`interactions` 신설, `links`의 의미 한정), 4장에 4층 파생 테이블 절 신설, 3장에 층별 저장 위치 한 줄
- PLAN 보강: 5.3 (가) `region_points.kind` 값. 5.3 (나)의 `embedding_distortion`·`metric_diagnostics` 컬럼은 ADR 0010·0013이 이미 보강했다
- PLAN 변경 이력: 채택 커밋에서 "ADR 0005 | 채택" 행을 더한다
- 코드·데이터: `schema/tables.py`(P4), `run_id` 키 검사, 임베딩 저장 API, `ingest`의 길이 단위 변환(km)

## 열린 점
- `regions.centroid`를 없애고 `region_points`로 일원화하는 안에 동의하는지(기하 중심은 계산)
- 섬 링크의 대기 시간을 어디에 둘지(사용자 결정). 섬 링크 시간은 시간표 소요 시간(관측)과 도착 권장 시간(대기 시간, 가정. 0S `island_links.csv`의 `wait_min`)의 합이다. 4항은 `links`에 관측값과 출처가 제공한 값만 두지만, PLAN G12·2-4는 섬 링크 시간(소요 + 대기)을 `links`에 넣는다고 한다. 0S는 섬 링크 시간(소요 + 대기) 전체에 ×0.5·×2를 곱해 민감도를 봤다(ADR 0013 5항). 한 가지 안은 소요 시간만 `links.travel_time`(`mode: air / ferry`)에 두고, 대기 시간과 민감도 배율은 설정 값(`config_json`)으로 두며, 둘을 더한 링크 시간을 4층 산출물로 보는 것이다. 섬 연결(G12)은 ADR 0007의 범위이므로 대기 시간의 기본값과 출처는 거기서 정한다
- 연결선 결과를 저장할 4층 테이블을 어느 ADR이 정할지(사용자 결정). PLAN 4.2에서 연결선(G8)은 이 ADR의 몫이고 ADR 0007의 범위는 4.1 질문 3, G12, G13이다. 이 ADR이 P4에서 정하거나, 0007로 넘기려면 영향에 "PLAN 4.2 보강: 0007 범위에 G8의 연결선 산출 테이블을 더한다"를 적는다. 0S는 연결선 5 km 초과 목록과 노드 매칭 점검 결과를 따로 남겼다
- `sources`의 표본 비율 컬럼은 P4에서 정한다
