# 0002-지역 ID와 코드 체계

- 상태: 제안 (0단계에서 확정)
- 날짜: 2026-10-20(제안), 2026-10-20(검토 반영 수정: 접미부·연도 정의, 영향, 열린 점)
- 관련: PLAN G1, G2, 6.2절 1-1·1-5 / DESIGN 4.2 `regions` / ADR 0003·0004

## 배경
DESIGN의 `region_id` 예시 `SGG_2025_11110`의 `11110`은 행정표준코드(행정안전부)의 종로구이고, 한국행정구역분류(국가데이터처, 구 통계청)에서는 `11010`이다. 한국행정구역분류가 7자리에서 8자리로 바뀌며 군 82개의 코드가 달라졌고(강화군 23310 → 23510), 행정표준코드도 강원(42 → 51)·전북(45 → 52)·군위군(47720 → 27720)과 2026년 전남광주 27개 시군구에서 바뀌었다. `source_code` 한 칸으로는 이 코드들을 담지 못한다. 경계가 그대로인 지역이 연도마다 새 ID를 받는지도 정해져 있지 않다.

## 선택지
ID 접미부는 그 상태의 기준 시점에 유효했던 행정표준코드 / 불투명 순번 중에서 고른다. 새 ID는 연도마다 / 지리적 실체가 바뀔 때만 발급하는 것 중에서 고른다.

## 결정
1. `region_id`는 프레임워크가 발급하는 고정 식별자이고 `{UNIT}_{YYYY}_{접미부}` 형식이다(예: 종로구 `SGG_2025_11110`).
   - UNIT은 `regions.unit`의 약어(SIDO, SGG, SI, EMD. ADR 0003)다. YYYY는 그 상태를 정의한 경계 기준 시점의 연도(2항)이고, 접미부는 그 상태의 기준 시점(YYYY-12-31)에 유효했던 행정표준코드(시도 2자리, 시군구 5자리, 읍면동 10자리)다. 발급 작업 날짜의 코드가 아니다(예: 광주 남구의 `base_2025` 상태는 `SGG_2025_29155`이고, 2026-07-01 이후의 코드 12270은 `region_codes`에만 둔다).
   - 접미부는 읽기 편하라고 붙인 이름표다. `region_id`는 만든 뒤 파싱하지 않고, 코드가 필요하면 `region_codes`에서 읽는다.
2. 새 ID는 지리적 실체가 바뀔 때만 발급한다. 바뀌지 않은 상태는 여러 기준 시점에 걸쳐 같은 ID를 쓴다. 연도는 프레임워크가 그 상태를 처음 등록한 기준 시점이다. `base_2025`를 먼저 정의하므로 2025-12-31에 유효한 상태는 2020년에 이미 있었더라도 2025다(예: 종로구 `SGG_2025_11110`). 2025-12-31 전에 끝난 2020 상태만 2020이다(예: 부천시 2020 `SGG_2020_41190`).
   - 발급 사유(하나라도 해당): (가) 하위 행정동 구성이 바뀜(분할·통합·이관. 예: 창원 의창구·성산구의 용지동 이관, 부천시 → 원미구·소사구·오정구, 인천 서구 → 서해구·검단구, 군위군 편입으로 대구광역시·경상북도, 광주광역시·전라남도 → 전남광주통합특별시). (나) 행정동 구성이 같아도 면적 변화율이 임계(가안 1%)를 넘음. 면적은 같은 출처·같은 일반화 수준의 두 판으로 재고, 후보는 관할구역 변경 목록(PLAN 1-5)과 대조해 확정한다.
   - 발급 사유가 아닌 것: 코드만 바뀜(8자리 개정, 강원·전북 개칭, 전남광주 통합에 따른 시군구 코드), 명칭 변경, 상위 시도만 바뀜(군위군 자신, 전남광주의 27개 시군구). 코드는 `region_codes`에, 이름은 `regions.name`에 반영한다.
   - 새 ID를 발급하면 이전 ID의 `valid_to`를 닫고 `region_crosswalk`에 행을 둔다(`effective_date` = 법령 시행일. 분류 기준일이 다르면 둘 다 `sources`에 적는다. PLAN 1-5).
3. `region_codes`(region_id, code_system, code, valid_from, valid_to)에 모든 코드를 둔다. `code_system`은 기관명이 아니라 체계 이름이고 값은 `admin_std`(행정표준코드), `kssc_7`·`kssc_8`(한국행정구역분류 7·8자리), `ktdb_zone`(KTDB 존 번호)이다. 새 체계는 같은 방식으로 더한다.
   - 같은 `(code_system, code)`가 기간이 겹치는 둘 이상의 `region_id`를 가리키지 않는다(스키마 검증).
   - 원천 자료의 코드는 (code_system, code, 자료 기준일)로 `region_id`를 찾는다.
4. `regions`의 한 행은 한 `region_id`(한 상태)이고 `valid_from`·`valid_to`는 그 상태의 유효 기간 [valid_from, valid_to)이다(null은 각각 처음부터, 현재까지). 상태가 바뀌면 이전 ID의 `valid_to`와 새 ID의 `valid_from`은 법령 시행일로 같고, `region_codes`의 기간도 같은 규칙이다. `parent_id`는 그 상태를 정의한 기준 시점의 상위 `region_id`다. `source_code` 컬럼은 두지 않고 원 데이터 코드는 모두 `region_codes`에 둔다.

## 영향
- DESIGN.md 수정 절: 4.2 `regions`(`region_id` 형식, `source_code` 삭제, `valid_*`·`parent_id`의 의미), `region_codes` 신설
- CLAUDE.md 규약: "지역 ID" 항의 "원 데이터 코드는 `source_code`에만 둔다"를 "`region_codes`에만 둔다"로 고친다(ADR 0004 영향과 같다)
- 채택 순서: ADR 0004와 0005 7항을 같은 커밋에서 채택하고, CLAUDE.md 규약 수정과 DESIGN 4.2 `regions.source_code` 삭제도 그 커밋에서 한다(ADR 0001 3항). 일부만 채택하면 CLAUDE.md의 `source_code` 규약, DESIGN 4.2, P4 스키마가 어긋난다
- PLAN 변경 이력: 채택 커밋에서 "ADR 0002 | 채택" 행을 더한다
- 코드·데이터: `spatial/`의 ID 발급·코드 조회 함수, `schema`의 `region_codes` 검증(기간이 겹치는 중복 금지), fixture `crosswalk_split_merge`

## 열린 점
- 접미부를 코드가 아닌 순번으로 둘지. 코드를 쓰는 안은 DESIGN 예시와 맞고 발급이 자료만으로 재현되지만, 코드가 바뀐 뒤에도 이름표는 기준 시점 코드로 남는다(`SGG_2025_29155`는 2026년 이후 광주 남구의 코드가 아니다). 순번을 쓰면 발급 기록을 `configs/reference/`에 두어야 한다
- `unit`만 바뀐 경우의 발급(사용자 결정). 부천시는 2020 `sigungu`에서 2024-01-01 `si`(ADR 0003 2항)로 단위만 바뀌었고 경계와 행정동 구성은 같다. 2항의 발급 사유에 들지 않아 같은 ID가 되지만, ID에 UNIT(SGG / SI)이 들어가고 4항에서 한 행은 한 상태이므로 같은 ID를 쓸 수 없다. 발급 사유에 "(다) `unit`이 바뀜(예: 부천시 `sigungu` → `si`, 2024-01-01). 경계가 같으면 `region_crosswalk`에 1:1 행을 둔다"를 더할지 정한다
- 면적 변화율 임계 1%는 근거 없는 가안이다. 1단계에서 판 사이 면적 차의 분포를 보고 정한다
- 상위 소속의 이력(군위군의 경북 → 대구)이 필요해지면 `region_codes`처럼 유효 기간이 있는 관계 테이블을 더한다. v1은 `base_2025`의 상위만 쓴다
- H3 셀의 ID는 4단계에서 정한다
