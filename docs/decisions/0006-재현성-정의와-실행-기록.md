# 0006-재현성 정의와 실행 기록 확장

- 상태: 제안 (0단계에서 확정)
- 날짜: 2026-10-20
- 관련: PLAN G10, 4.1절(λ 프리셋), 5.4·5.5절, 6.3절 완료 기준, 11.1절 / DESIGN 4.2 `runs`, 9.2 / ADR 0010·0013

## 배경
DESIGN의 `runs`(run_id, scenario_id, config_hash, data_snapshot, code_version, seed, created_at)로는 같은 commit이라도 의존성 버전이나 미커밋 변경이 달라 생기는 결과 차이를 잡지 못한다. 설정 해시를 어떻게 만드는지, 결과가 "같다"는 것이 무엇인지도 정해져 있지 않다.

## 선택지
`code_version`만으로 재현을 주장하기 / 환경 잠금 해시, 미커밋 표시, 해석된 설정 전문을 함께 기록하기.

## 결정
1. `runs` 컬럼: run_id, scenario_id(기준선이면 `baseline`), parent_run_id(시나리오 → 기준선), status(`running` / `succeeded` / `failed`), config_hash, config_json(기본값을 채운 설정 전문), data_snapshot, code_version(git commit), code_dirty, env_lock_hash, python_version, platform, seed, created_at. 실행을 시작할 때 `running`으로 기록하고 끝나면 바꾼다. `succeeded`가 아닌 run의 산출물은 읽지 않는다.
2. 같은 실행 조건은 `config_hash`, `data_snapshot`, `code_version`(`code_dirty = false`), `env_lock_hash`, `seed`가 모두 같은 것이다. 이 조건이 같으면 3항의 결과 동일성을 만족해야 한다.
3. 결과 동일성(PLAN 5.4): 결정적 단계(최단경로, 곡률, 배분)는 산출 테이블의 내용 해시가 같아야 한다. 최적화 단계(임베딩)는 CPU·단일 스레드에서 해시 일치를 목표로 하고, 최소한 왜곡 지표가 상대오차 1e-6 이내여야 한다. 환경이 다르면(`env_lock_hash`, Python 버전, OS·CPU) 해시 일치를 요구하지 않고 허용오차로 비교한다.
4. 해시 규칙
   - `config_hash`: 기본값까지 채운 설정 객체를 키 정렬 JSON(UTF-8, 공백 없는 구분자, NaN·무한대 금지)으로 직렬화한 SHA-256이다. YAML의 공백·주석·키 순서가 달라도 같다. 프리셋은 이름과 해석된 값을 모두 `config_json`에 남긴다(PLAN 4.1).
   - 파일 해시는 바이트의 SHA-256이다. `data/raw/` 원자료는 바이트 그대로 구한다. 저장소에 들어가는 텍스트 파일(`configs/reference/`의 CSV, `uv.lock`)은 줄바꿈을 LF로 바꾼 내용으로 구한다. 작업 트리에 CRLF가 남아 있어도(2026-10-20 확인: 0S의 `island_links.csv`는 저장소에는 LF, 작업 트리에는 CRLF다) 해시가 같아야 하기 때문이다.
   - 테이블 해시는 파일 바이트가 아니라 내용(키로 정렬한 열 단위 값)으로 구한다. Parquet 파일은 쓴 도구의 버전과 메타데이터에 따라 바이트가 달라지기 때문이다.
   - `env_lock_hash`: `uv.lock`의 SHA-256이다(LF 정규화).
5. 미커밋 표시: `code_dirty`는 `git status --porcelain`(무시 대상 제외)이 비어 있지 않으면 true다. `code_dirty = true`인 실행은 탐색용이며, 기준선으로 등록하거나 시나리오의 `parent_run_id`로 쓸 수 없고 보고서에 탐색용이라고 표시한다(PLAN 5.4, 11.1). git 정보를 읽을 수 없으면 실행하지 않는다.
6. 입력 검증: `data/raw/` 파일은 실행이 읽을 때마다 `sources.file_hash`와 대조하고, 다르면 중단한다. `data_snapshot`에는 읽은 `source_id`와 `file_hash`, 읽은 processed 테이블의 이름과 내용 해시, 쓴 OD의 기준연도·존 체계·변환 경로, 추정 OD 사용 여부를 남긴다(PLAN 6.3절 완료 기준, G7).
7. 난수: `core.seed`가 `seed` 하나로 `random`, `numpy`, `torch`를 맞춘다. 단계마다 `numpy.random.SeedSequence(seed).spawn`으로 독립된 하위 시드를 받아, 한 단계가 난수를 더 써도 다른 단계의 결과가 바뀌지 않게 한다(재표본과 임베딩 재시작이 서로 다른 난수열을 쓰는 ADR 0010 6항과 같은 취지다).
8. 식별과 저장: `run_id`는 UTC 시각과 `config_hash` 앞 8자로 만든다(예: `20261101-093012-3fa9c1d2`). 짧아서 `data/derived/run_id=<id>/` 경로가 Windows 경로 길이 제한(PLAN 5.5)에 걸리지 않는다. `runs`는 run마다 `data/derived/run_id=<id>/runs.parquet`에 한 행으로 쓰고 전체 조회는 DuckDB의 glob 읽기로 한다. 공용 파일을 갱신하지 않으므로 충돌이 없다.
9. 시나리오: `parent_run_id`가 가리키는 기준선의 `data_snapshot`과 계산 설정을 그대로 쓴다. 기준선과 `code_version` 또는 `env_lock_hash`가 다르면 `runs`와 보고서에 표시한다.

## 영향
- DESIGN.md 수정 절: 4.2 `runs`(컬럼 확장), 9.2(절차 1: 기준선 run을 `parent_run_id`로 고정, 절차 5: 기록 항목)
- CLAUDE.md 규약: "모든 실행은 `runs` 기록(config_hash, data_snapshot, code_version, seed)을 남긴다"에 `config_json`, `code_dirty`, `env_lock_hash`를 더한다
- PLAN 보강: 5.4 `runs` 항목에 `python_version`, `platform`, 텍스트 파일 해시의 LF 정규화
- PLAN 변경 이력: 채택 커밋에서 "ADR 0006 | 채택" 행을 더한다
- 코드·데이터: `core/hashing.py`, `core/runs.py`, `core/seed.py`(P3). 테스트: 공백·주석·키 순서가 달라도 같은 해시, dirty 감지, 테이블 해시가 쓰기 도구와 무관함, CRLF·LF 파일의 같은 해시, 하위 시드의 독립

## 열린 점
- 시나리오와 기준선의 `code_version`·`env_lock_hash`가 다를 때 표시만 할지 거부할지
- `docs/`만 바뀐 작업 트리도 dirty로 볼지(위 안은 포함한다)
- `python_version`, `platform` 컬럼은 PLAN에 없는 추가다
